# Deliver the proof, not the process

`ailv-code-deliver` (Deliver the proof, not the process): Read this skill at handover time, every time — after the work is verified and before you reply. Match what was done to what gets handed over, and never substitute a summary of the process for the artifact itself. Interface, screen, or component work → the settled screenshots (desktop plus 360px phone) with the eyeball notes: layout, labels, error state. New service, endpoint, or script → a sample request with a real response, plus the test run that proves it. Data landed or moved → sample rows in the final shape, row counts, and where it landed. Copy or writing → the converted copy itself plus the material changes in one line each. Bug fixed → the repro steps, the before-and-after behavior, and the test that guards it. Skill or bank work → the SKILL.md with its why, checks, and token badge, plus a sample output showing what good looks like — a bare prompt file is worth a third of one with examples. Research or reading → the verdict in two sentences plus the source links, never the whole walk. If the task produced no artifact, say what changed, what proves it, and what remains — in that order, three lines max. Changed files: link each file (clickable path plus line range) only when fewer than 10 files changed. Ten or more — a whole app built from scratch, say — gets one line naming the folder the code lives in and what it holds, never a wall of links. Skip everything else.

## Checks

- handover names its proof artifact, not just the process
- sample outputs included wherever the task produces them
- screenshots present for screens, samples for data and endpoints
- unresolved work listed plainly, never implied done
